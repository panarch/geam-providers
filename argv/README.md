# geam-argv

This crate implements the private Erlang external of the unchanged [`argv` 1.1.0](https://hex.pm/packages/argv/1.1.0) Gleam package through Geam's public typed provider API. Add `argv` to the Gleam project and select `geam-argv` as its provider. The verified package range is 1.1.0 only. The [standalone fixture](fixtures/gleam/) and [Rust embedding fixture](fixtures/embedding/) use the original Hex package.

`argv.load().arguments` contains the application arguments in order. For standalone execution, put them after Geam's `--`, for example `geam run -- --flag key=value`. Geam's runner controls do not enter this list. A built application reads its own process arguments. The default provider state captures the arguments once when a run begins; repeated calls return the same values. Rust embedding hosts can construct `RunState::new(runtime, program, arguments)` and project it through `HostComponentProfile<geam_argv::Component>` to supply an explicit snapshot.

By default, `runtime` is the host executable path and `program` is the host working directory at provider initialization. Geam runs the generated standalone runner from the Gleam project directory. A built application started elsewhere and a Rust embedding host may use another working directory. The original Erlang FFI also uses the working directory when no escript path is available; the JavaScript FFI uses its script path. These runtime-specific paths need not be byte-for-byte equal across targets. On hosts with non-Unicode process arguments or paths, this provider uses lossy Unicode replacement because the upstream API returns `String` without a conversion error. An unavailable executable path or working directory fails provider initialization before Gleam source executes.

The repository pins Geam to `main` commit `b23d82a23d31c77eca749d18f67e73f0d9d952c7`. See the [testing guide](../docs/development/testing.md) for fixtures, coverage, and packaging checks. Publishing a crate and consuming a published Geam release are separate steps.
